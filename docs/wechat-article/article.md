# python-pi：开源的多租户 coding agent harness

> python-pi 的底座是 pi——11 个 npm 包、约 18 万行 TypeScript 的终端 coding agent。我们保留它最值钱的部分（语义契约、会话格式、命令协议、依赖极简），用 Python 重写了实现，并补上四块上游没有的能力：**浏览器 UI、团队多租户、容器沙盒、治理与审计**。18 万行收敛到 25.2k 行，588 个测试全部离线可跑。
>
> 下面按三件事讲：**继承了什么、改进了什么、创造了什么。**

## 一、继承：pi 有四个地方值得原样抄下来

选 pi 作底座不是因为它最流行，而是因为它的四个设计决定经得起看。

### 1.1 极简内核 + 严格分层，每一层都能单独用

![分层架构](assets/arch.png)

- **pi-ai（5.6k 行）**——provider 抽象。消息/内容块/Usage/Model 的类型与 JSON 互转、12 种流式事件的 `EventStream`、provider 注册表、Anthropic 与 OpenAI 兼容适配器、工具参数校验、成本计算。
- **pi-agent-core（1.8k 行）**——agent 循环（steering / follow-up / 工具批 / 中止语义）+ `Agent` 状态机。**1.8k 行，可以单独拿去驱自己的工具。**
- **pi-coding-agent（14.7k 行）**——全部业务：JSONL v3 会话树、7 个内置工具（read/write/edit/bash/grep/find/ls）、系统提示词组装、skills、settings、会话编排、print/json/rpc 三种模式、扩展协议。
- **pi-server（3.1k 行）**——这一层是我们加的，见第三节。

依赖严格单向，拿到任意一层都能单独用。**核心三层加起来只引入两个第三方包**：httpx 和 pyyaml，pi-agent-core 一个新依赖都没加。上游用到的 typebox、partial-json、proper-lockfile 这些，我们用内联实现、json 容错解析和标准库顶掉了——**能自己写三十行解决的，就不装一个包**。

这条哲学我们原样继承了，因为它直接决定这套东西能不能被嵌进别人的服务里。

### 1.2 会话就是一个文件，不是黑盒数据库

![会话文件与分叉](assets/session-tree.png)

会话是 JSONL、version 3，靠 `id` / `parentId` 构成**树**：分支**在原地发生**（同一个文件里继续 append，新 entry 的 parentId 指回分叉点），只有 `fork()` 才把 root→entry 复制进新文件。还有个必须复刻的怪癖：**第一条 assistant 消息落盘之前，不创建文件。**

**为什么值得继承**：会话是这类工具最贵的数据资产。存成可读、可 diff、能手工编辑的文本，意味着出问题时你可以直接打开看，而不是先连数据库、再写查询。

### 1.3 流式事件是有契约的，不是"随便发点 JSON"

12 种事件，成功是 `start → updates* → done`，生成开始后失败是 `start → updates* → error`，setup 失败则直接 `error`（没有 start）。

契约里最反直觉的一条：**`partial` 是所有事件共享的同一个可变对象，原地修改**，不是每事件的快照。如果你习惯性地把 `event.partial` 存进列表准备"最后统一处理"，拿到的会是**同一个对象的最终态**，前面几帧全丢。省内存，但要求消费者懂规矩——这种取舍上游做得很克制，我们原样留着。

### 1.4 上游把行为边界写死了，所以语义可以逐字对齐

这是能做成这件事的真正前提：**pi 把每个行为的边界都写死了**——两个 API 可以错误处理方式相反，同一个项目里能有两种时间戳单位。这些不是脏代码，是被测试钉死的**可观察契约**：顺着走，断言可以直接抄上游测试；自己发挥，每个偏差都得单独设计验证。

## 二、改进：三件我们主动做的事

### 2.1 只搬核心：18 万行 → 3 万行

改的第一步其实是**克制**。逐层读完上游源码后，有三个结构性发现直接决定了边界：

- **裸 agent 循环是自包含的**：types、agent-loop、agent、stream-fn 四个文件约 1.6k 行，对 harness 目录**零 import**；而 harness 那约 12k 行是附加的持久化运行时，不是必需品；
- **chord 的完整内核只在实验代码里用**，experimental 目录之外没有任何非实验代码 import 它；
- **CBOR 远程栈和 `--mode rpc` 是两套协议**，前者是实验性的，后者才是稳定的集成方式。

顺着这三条推，"不搬清单"就出来了：TUI（18k 行）、harness 持久化运行时、CBOR 协议栈、SQLite 会话后端、telemetry、evals。**18 万行 → 3 万行，差的不是能力，是刻意不搬。**

### 2.2 落到 Python 生态里，是两处真实的改动

**能嵌进 Python 技术栈。** 上游只能嵌进 Node 服务；现在的四层库 `uv add` 就能用，一个完全离线的例子（真实工具 + 真实会话落盘，用确定性 provider 替代 LLM）只要 `uv run python examples/offline_agent.py`。

**扩展系统换成了 Python 原生的。** 上游扩展是 TypeScript，而我们**没有做跨语言兼容**——这是刻意的：扩展 API 里 renderer 返回组件、同进程 `AbortSignal`、参数原地修改这些语义**无法跨 RPC 边界存活**，硬做只能做成一个残缺子集。所以 Python 侧另设计了一套原生插件协议：一个普通模块暴露 `setup(pi)`，就能注册工具、命令或拦截事件——拦截一次 bash 调用只要十来行。

### 2.3 语义保真：那条"不许改"的线

这是全文最重要的一节。**改进的前提是不许乱改**——16 条可观察契约一条没动，挑四条最反直觉的：

**① `stream()` 绝不因 setup 失败抛异常**（编码成 `error` 事件），而 **`stream_simple()` 可以同步抛**。同一个库里的两个 API 错误处理方式刻意相反，因为**首次配置检测依赖同步抛出**。出于"统一风格"把它们改成一致，就会静默破坏调用方的初始化探测。

**② `stop_reason == "length"` 时，整批工具调用都不执行。** 不是"执行一部分"，也不是"执行到哪算哪"——全部报错，让模型重新发起。

**③ 两处 hook 的异常语义不同。** `before_tool_call` 抛异常 → 变成一个 error tool result；`after_tool_call` 抛异常 → **结果被丢弃**。同样是抛异常，两条路径的后果完全不同。

**④ Python 最容易踩的一条**：`dict.get()` 把"显式 null"和"没有这个键"合并了，而它们的语义完全不同。

```python
# 错：把「显式 null」和「没有这个键」当成一回事
if mapping.get("minimal"):
    ...

# 对：键不存在 = 用 provider 默认；显式 null = 不支持
if "minimal" in mapping and mapping["minimal"] is not None:
    ...
```

其余 12 条里最容易被"顺手改掉"的几个：

- `EventStream` 是 push 队列：完成事件本身仍要投递给迭代方，`result()` 在首个 done / error 时即 resolve，**不等 `end()`**；
- `terminate` 只有批次内**每一个**结果都满足时才终止循环；`AbortSignal` 是**被观察的标志**，不是 `CancelledError`；
- 并行工具执行：`tool_execution_end` 按**完成顺序**发，但 toolResult 消息按**源顺序**装配；
- **消息时间戳是毫秒整数，会话 entry 的时间戳是 ISO 字符串**——同一个项目里两种单位。

## 三、创新：上游没有的四块

前面都是"把别人的好东西搬过来"，这一节是上游完全没有的。

### 3.1 一套协议，两种传输

![一次 prompt 的链路](assets/flow.png)

上游只有终端 TUI 和 stdio 上的 `--mode rpc`。我们**没有重写那 18k 行的差分渲染器**，而是补了一个浏览器 UI——关键在于**它没有另造第二套 API**：浏览器说的就是 `--mode rpc` 那套协议，只是把传输从 stdio 换成 WebSocket。30 个命令（`prompt` / `fork` / `compact` / `get_tree` …）原样复用，不支持的 3 个会返回带原因的错误响应，而不是静默挂起。

所以任何为 pi RPC 写的客户端，改个地址就能连浏览器这层；反过来，这里验证过的协议行为对 stdio 同样成立。这是团队模式下的真实界面——会话、用量、成员管理、审计，全部建在同一套协议之上：

![浏览器 UI](assets/ui.png)

顺手记三个协议层的坑，都不是"写错了"，而是"想当然会死"：

1. **帧层不能用 `splitlines()`**——严格 LF 分帧的 JSONL，而 Python 的 `str.splitlines()`（以及 Node 的 `readline`）会把字符串**内部**的 U+2028 / U+2029 当成换行，把一条记录撕成两半。
2. **出站帧必须用与 stdio 相同的序列化器**——传输换成 `emit` 回调后，若用严格编码的 `send_json`，遇到非纯 JSON 载荷会抛异常，而**同步回调没法把异常传回去**，发送任务静默死掉，表现为"流到一半卡住"。
3. **对话框只发给一个标签页**——同一个 `confirm` 在三个标签页同时弹出、再等最先作答的那个，比只问一次更糟。

### 3.2 多租户：从"一个人用"到"一个团队用"

加 `--auth-mode team` 就能内网多人共用，每人一个工作区、一个独立会话，互不可见；用量按 uid 记账、可设月度上限；工具调用全程留审计。有三处**必须这么做**：拒绝加载用户扩展（per-uid 的扩展目录等于给每个同事一个**以服务进程权限运行的 RCE 入口**，所以政策扩展是内置、强制加载、不可关的）；子进程环境按变量名白名单构造、剔除 `*_KEY` / `*_TOKEN` / `*_PASSWORD`，共用的 API key 也不能走命令行参数（`ps aux` 对同机所有账号可见）；`bootstrap` 的 `SystemExit` 要收敛成 `BootstrapError`，因为它继承自 `BaseException` 而不是 `Exception`，会直接击穿请求处理。

### 3.3 容器沙盒，以及一句必须说的话

**白名单 + 审批不是沙盒。** 它防的是误操作，防不住恶意；真实边界是容器——`PI_SANDBOX_BACKEND=provisioner` 时，agent 的每条命令都在一个只挂载该用户工作区的容器里执行，有一个只挂 `docker.sock` 的 provisioner 服务负责起停与空闲回收。而且要老实说清两条：沙盒**只覆盖命令执行**，`read`/`write`/`edit` 仍由服务进程直接读写工作区；会话状态在进程内存里，**单进程是硬约束**，横向扩展得先换掉注册表。

这句话我同时写进了文档、代码注释和界面提示——**不给使用者虚假的安全感**，比多一个特性重要。

### 3.4 跨语言会话互通

会话格式本身是继承来的，但**让两种语言真的互读，是新的**：Python 版能读 pi 写的会话，pi 也能读 Python 版写的；字段名逐个对齐（`stopReason` / `toolCallId` / `cacheRead` …）、`undefined` 省略语义一致、能读 v1/v2 并在写回时迁移到 v3。

这意味着你可以在终端里用 pi 接着浏览器的对话继续干活，反过来也一样。代价是会被上游 schema 绑住——明确的交易，不是免费的。

## 四、这些能力靠什么撑住：588 个离线测试

**31 个测试文件、588 个测试函数、14.8k 行，全部离线，不访问网络、不需要任何 API key。** 三根支柱：

**1. 契约对齐。** 关键行为是逐字对齐而不是"大致相同"，所以断言可以直接抄上游测试——agent 循环的 12 事件序列就来自上游的断言。

**2. 黄金用例。** 会话存储有手工构造的 v3 JSONL 黄金文件，验证读取、上下文重建与再序列化——字节保真度还用 node 的 `JSON.stringify(JSON.parse(line))` 交叉验证过。

**3. 真实线格式。** provider 适配器用 `httpx.MockTransport` 喂入固定的 SSE 字节，断言到**请求体字段级**——不是断言"调用了某个方法"，而是断言发出去的 JSON 长什么样。

再往上一层是 **CLI 端到端**：起一个本地假 OpenAI 兼容服务，以**子进程**运行真实的 pi-py，从加载配置一路走通流式响应、工具执行到落盘会话。这些**全是确定性的**，CI 里没有 flaky。

## 五、明确不做的事，和已知的坑

- **没有对真实 provider 做过在线验证**——开发环境没有任何 API key。首次接入时请先用小 prompt 验证适配器，别直接上生产。这是最大的验证缺口，不想含糊过去。
- `grep` / `find` 是纯 Python 实现（不依赖 ripgrep / fd），`.gitignore` 支持是简化版，语义是"接近"而非逐字节相同；
- 内置的 `edit` 工具不做上游模糊匹配兜底之外的全部启发式；
- 工具越界只由政策扩展拦，`cd /elsewhere && rm -rf *` 这类"先改目录再操作"识别不了；

## 六、开源地址与几个判断

```text
https://github.com/johnson7788/python-pi
```

MIT 协议，与上游一致。仓库里是四层可独立使用的框架库 + 一个浏览器 UI + 一套 Docker Compose 的团队部署（含沙盒 provisioner），以及 588 个离线测试。

几个判断，供你按需取用：

- **如果你在找一个能复用的 agent 底座**：`pi-agent-core` 只有 1.8k 行，可以绕开编码助手那层单独用。
- **如果你在设计 agent 框架**，两点值得抄：`partial` 这种"共享可变对象"的取舍（省内存，但要求消费者懂规矩）；以及把 **preflight 和执行分开**——配额、白名单、危险命令都在 preflight 判，用户不用等模型跑完才发现被拒。
- **如果你在给 agent 加多租户**，"这不是沙盒"这句话要早点说——把边界讲清楚，比让人误以为安全强。
- **如果你在为没有 API key 的 CI 发愁**，`httpx.MockTransport` 断言到字段级 + 假 provider 起子进程跑端到端，这套组合拳值得抄。

最后一句：**上游那份代码最值钱的地方，不是它实现了什么，而是它把每个行为的边界都写死了。** 继承的时候，这些"写死的地方"就是扶手——顺着扶手走，三天能干完三周的活。
